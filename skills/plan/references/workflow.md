# plan workflow

- 依頼、成功条件、制約、既存差分、局所ルールを確認する。
- 必須入力が不足、または相互に矛盾する場合は plan を確定しない。不足する事実は `research`、判断が必要な不明点は `grilling` に戻す。
- 計画中は repo-tracked file、既存未追跡ファイル、Git index、外部状態を変更しない。install、generate、write、test、build 等も実行しない。
- `research` の事実、`grilling` の決定事項、未確認事項、推測を分ける。
- 対象ファイル、既存の参照実装、依存、公開 API、データ移行の影響を必要な範囲だけ調べる。
- 計画を左右する不明点だけ質問し、コードから確認できることは質問しない。

## 粒度と責務

- 計画の各項目を、独立して実装・テスト可能な一つの変更単位にする。規模の大小より独立性を優先する。
- 小さく明確な変更は短い計画にし、不要な設計や調査を追加しない。
- plan でアーキテクチャ、変更対象ファイル、公開 API / interface、共有される命名、採用する既存 abstraction と依存、主要な制御フロー、状態変更、データフロー、エラー処理、互換性、migration 方針、テスト観点、完了条件を確定する。
- 設計判断とは、外部仕様、構造、依存、公開・共有される契約、主要な分岐、状態変更、エラー時の振る舞い、互換性、migration、テスト戦略に影響する選択を指す。これらは採用案を一つに決め、implement に選択肢を残さない。
- 実装担当に委ねるのは、設計を変えない private な局所表現、軽微な命名、import 整理、formatter 対応、確定済み設計の定型的な実装展開だけにする。
- 「認証を修正する」「テストを追加する」のような抽象的な項目や、行番号単位の手順は出力しない。
- 判断の前提となる事実は `research`、要件・優先順位・トレードオフの選択は `grilling` で解消する。

## 実装項目と検証

- 変更対象をファイル単位の独立した実装項目へ分割し、次の形式を基準にする。

  ```text
  1. path/to/file (新規 / 変更 / 削除)
     - 対象: 関数、型、schema、route、設定など
     - 設計決定: 採用する構造、既存パターン、依存、公開・共有契約、主要な分岐
     - 変更: 振る舞い、入出力、条件分岐、既存呼び出しへの影響
     - データフロー: 入力から保存・処理・応答まで
     - エラー・互換性・migration: 失敗時の扱い、既存利用者への影響、移行方針
     - テスト: 正常系、境界値、異常系、回帰観点
     - 完了条件: この項目単独で判定できる条件
  ```

- 該当しない欄は「なし」と明記し、実装担当に判断を残さない。単一ファイルかつ低リスクの変更では、該当する欄だけに絞ってよい。
- 実装項目を並べた後、実装順序、再利用する既存パターン、対象外、全体の Definition of Done、`test` へ渡す実装契約を定義する。受入条件は、実装担当と test がコマンドや期待結果で判定できる形にする。
- lint、typecheck、test、build など test で実行する検証を、変更範囲とリスクに応じて選ぶ。
- 各検証は command、対象、期待結果、副作用を記載し、必要な場合だけ timeout、外部アクセス、並列実行条件を追加する。

## 完了ゲート

- 各設計判断について採用案が一つに確定し、implement が代替案を選ぶ必要がない。
- 各実装項目を単独で渡しても、設計、仕様、対象ファイル、エラー処理、互換性、テスト方針について追加質問が発生しない。
- 実装裁量が、設計を変えない局所的な範囲に限定されている。
- 「必要に応じて」「適切に」「可能なら」のような、判断を implement に委ねる表現が残っていない。
- 実装に影響する未確認事項、推測、複数候補が残る場合は最終計画を出力せず、事実不足は `research`、意思決定は `grilling` に戻す。調査や質問では解消できない事項は、断定せずに前提条件と、前提が崩れた場合の影響として明示する。
- 計画を確定できない場合は最終計画を出力せず、確定済み事項、未解決点、次に使う skill だけを示す。
- 出力前に計画を全文再構成する。最終出力は、会話の経緯を知らない読者が計画本文だけで実装と検証を開始できる自立した文書にする。検討順、撤回済みの案、比較過程、未定義の指示語や「前述のとおり」のような経緯依存表現を残さず、現在の事実、決定事項、制約、対象外、前提だけを現在形で記載する。
- 出力は少なくとも「目的と成功条件」「前提と決定事項」「設計判断」「変更対象と実装項目」「実装順序」「対象外」「実装契約」「検証」「リスクと未解決の前提」に分ける。
