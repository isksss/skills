# plan

Tech Lead / 設計者として、依頼とコードベースを調査し、経緯を知らない SE3年目程度の新規参画者でも計画本文だけで実装と検証を開始できる変更計画を作る。計画には、何をなぜ変更するか、どのファイルのどの識別子をどう変更するか、変更後に何を確認すれば完了かを具体的に記載する。

設計判断は plan で採用案を一つに確定し、implement には設計を変えない局所的な実装だけを委ねる。計画の検討過程、撤回した案、会話への参照、読み手が補わないと理解できない「前述のとおり」などの経緯依存表現は最終出力に残さない。計画中は repo-tracked file、既存未追跡ファイル、Git index、外部永続状態を変更せず、ファイルを書き換えるコマンドや検証コマンドを実行しない。

## Workflow

`references/workflow.md` を読む。

## Output

- 目的、スコープ、成功条件。利用者またはシステムの変更前後の状態を含める
- 実装開始時点の前提、制約、用語。事実、決定事項、未確認事項、推測を区別する
- 設計判断一覧。各判断の採用案を一つと、採用理由または制約を記載する
- 変更対象ファイルと実装項目。ファイルパスだけでなく、関数、型、schema、route、設定キーなどの対象識別子を示す
- 実装順序と、参照する既存実装のパス・識別子・再利用理由
- 対象外。今回変更しない機能、ファイル、移行、運用作業を明示する
- `test` へ渡す実装契約。受入条件、確認対象、既存差分の扱いを含める
- 全体の Definition of Done。実装・テスト・ドキュメント・互換性の完了条件を判定可能な形で示す
- `test` で実行する検証。コマンド、実行場所、対象、期待結果、副作用、timeout、外部アクセスの有無を記載する
- 互換性、セキュリティ、残リスク
- 未解決の前提。実装に影響する事実不足は `research`、意思決定不足は `grilling` に戻し、確定できるまで最終計画を出力しない
